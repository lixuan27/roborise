RoboRISE: Benchmarking Recursive Self-Improvement through Long-Horizon Robotic Execution

A benchmark for robot agent systems, where the unit under test is the whole system rather than a language model or a control policy on its own.

Problem definition

The benchmark measures whether a robot agent can turn task understanding, visual perception, planning, control and execution feedback into one closed loop, and finish tasks that range from basic manipulation to long horizon reasoning and dexterous work while respecting the task rules and the physics. What is measured is the complete agent system, which includes the base model, the prompts, the task state it maintains, the tools it calls, the code it executes and the robot control program it writes.

Input, closed loop execution and output

The input is the task goal, the visual and proprioceptive observation that the current level allows, and the set of tools the agent may call. The agent commits to no complete trajectory in advance, and instead repeats observation, planning, action, feedback and correction throughout execution. At step t it selects a tool call and a robot action from the current observation and its own task state, the environment applies the action and returns the next observation, and the agent updates its state and then decides whether to continue, to look again, to replan or to attempt recovery.

c_t = pi_tool( G, M_t, O_t^L ; U^L )        r_t = U^L( c_t )
a_t = pi_act ( G, M_t, O_t^L, r_t )

x_{t+1} = F( x_t, a_t )                    O_{t+1}^L = H_L( x_{t+1} )
M_{t+1} = Update( M_t, O_{t+1}^L, r_t, a_t )

tau_A   = { O_t^L, c_t, r_t, a_t } for t = 0 .. T
Eval( tau_A, x_{0:T} ) = ( S_task, S_rule, S_physics, E )

Here M_t is the task state the agent maintains, r_t is what a tool returns, and E is the auditable evidence, meaning video, observations, trajectories and call logs. Environment feedback returns to the agent and shapes later actions, and the ground truth state and the success decision held by the evaluator stay outside the control loop.

Why now

Recent work has started to place language models and coding agents inside the robot execution loop.

  • CaP-X lets an agent compose perception and control primitives, generate executable programs and improve them through multi turn interaction, execution feedback and visual differences. Its results also show that performance still depends heavily on hand designed tool abstractions and scaffolding. [1]
  • Claude Plays Robotics compares control interfaces that include low level actions, Python controllers, reinforcement learning and pretrained policies. Model behaviour depends strongly on the interface, and in the low level setting the full task success rate stays near 0 to 5.5 percent. [2]
  • Gemini Robotics 2 combines vision language action control with embodied reasoning for spatial reasoning, multi step planning and dexterous manipulation. [3]
  • ASPIRE diagnoses failures from robot rollouts, edits the control program, executes again and stores reusable skills, which makes closed loop execution and program iteration explicit. [4]
  • ENPIRE brings a coding agent into real robot policy improvement, so it revises a policy from video, trajectories, rewards and failure cases and keeps experiments running through automatic evaluation and automatic reset. [5]

Together these results show that agents can already build and operate robot control systems. The observation permissions, tool interfaces, training data and hand written scaffolding differ across systems, which leaves the published numbers hard to compare.

Why it matters

Robot benchmarks today mostly cover short grasping, placing or navigation tasks, while a real task often consists of tens or hundreds of dependent steps. Tidying a bookshelf, assembling from a drawing and solving a Rubik cube ask for more than locally correct motions. They ask the agent to:

  • maintain task state and constraints over a long horizon
  • compose vision, grasping, motion planning and control tools correctly
  • judge from the actual result whether an action did what it was meant to do
  • replan after a grasp offset, a collision or a state estimation error
  • avoid error accumulation, rule violations and unrecoverable failures
  • finish the task without privileged simulator information

The benchmark therefore focuses on long horizon state maintenance, tool composition, closed loop correction and failure recovery.

Access levels

A level states what observations, tools, simulator information and training rights the agent may use. All levels share the same task rules, action space and success criteria, and the levels are nested from 1 to 4.

LevelAllowedRestricted
Level 1, RGB geometryRGB, camera calibration, proprioception, robot model, depth estimation, three dimensional reconstruction, inverse kinematics and motion planningnative depth, object ground truth, contact information and evaluator state
Level 2, generic grasp modeleverything in Level 1 plus frozen generic grasping and contact modelsfinetuning any model on benchmark data
Level 3, privileged simulationeverything in Levels 1 and 2 plus official simulator state, contact and rollout for online search and optimisationtraining a task specific policy that persists across episodes
Level 4, task trained policyeverything in Levels 1 to 3 plus a task specific policy trained on task datatest scenes, test trajectories and evaluator state stay hidden

Level 1 may use optimisation tools such as SciPy and cuRobo and may build an approximate scene model from RGB. What separates Level 3 from Level 1 is reading official simulator ground truth rather than using optimisation. Any policy whose parameters are trained on benchmark task data and kept across episodes belongs to Level 4.

Low level runtime libraries such as MinkowskiEngine are recorded as implementation dependencies rather than agent tools. Tools such as cuRoboV2, Stream3D and SAM3D join the whitelist once their interfaces and versions are pinned.

Evaluation

A run counts as a valid success only when task success, rule compliance and physical validity all hold: S_valid = S_task and S_rule and S_physics. The reported numbers are task success rate, valid success rate, rule violation rate, physical failure rate, subgoal completion, recovery rate, execution time, action steps, tokens and tool calls. Every experiment stores the trajectory, the video, the observations the agent actually received, the tool calls, the code edits and the evaluator log, so a failure can be traced and privileged information leaks can be checked.

Experiment

Stage one compares how well coding agents build robot control systems, with Codex, Claude Code, Kimi Code and DeepSeek Code. An agent may read documentation, write code and run experiments in the public training scenes, and revise its program from video, trajectories and evaluator feedback. Once the development budget is spent the code is frozen and evaluated on hidden test scenes.

Task typeDevelopment timeToken budget
Gripper24 hours10M
Dexterous hand72 hours30M

All agents share the same repository, tool documentation, training scenes, action interface and hidden test scenes. Each run outputs the robot trajectory, the execution video, the evaluator results, the tool and model call logs, and the time, token and compute cost. Stage one can start from the gripper tasks and Levels 1 to 3, with the dexterous hand, online agent execution and Level 4 policy training left as extensions.
